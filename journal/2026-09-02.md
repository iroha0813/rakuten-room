# 作業記録 2026-09-02（6日目）

朝の候補生成がまた止まっていた。8/29, 8/30, 9/1に続き4回目の同一障害
（回線IPの変動によるRakuten API 403 CLIENT_IP_NOT_ALLOWED）。

## 症状

`local/logs/2026-09-02.log`（07:00の自動実行分）。

```
現在のグローバルIP: 59.132.67.121
```

## 気づいたこと（未解決のまま記録）

直近の実測グローバルIPを並べると、同一ISP内の近いレンジという前提が崩れている。

| 日付 | 実測グローバルIP |
|---|---|
| 8/30 | 59.132.56.172 |
| 9/1  | 220.146.83.217 |
| 9/2  | 59.132.67.121 |

`59.132.x.x` と `220.146.x.x` という**別ブロック**を行き来している
（8/30の記録にある登録済み4件にも `106.155.52.110` があり、3ブロック以上を確認済み）。
8/30時点で検討していた「CIDRで範囲登録すれば変動に耐えられる」という対策は、
この振れ幅を見る限り有効性が低い可能性が高い。カバーしようとすると許可範囲が
広くなりすぎ、IP制限の意味が薄れる。

## 対応

ユーザーが `59.132.67.121` をRakuten Developers側で登録済みだったため、
`scripts/run_daily.ps1` を12:48に再実行し復旧を確認。

```
候補プール 267件（日用品59 / ガジェット88 / 食品120）→ 5件選定
コミット「候補生成 2026-09-02」を push
```

## 残っている懸案（更新）

- **失敗時の通知がない**点、依然未着手。今回も気づけたのはユーザーが能動的に確認したため。
- **CIDR化は根本対策にならない可能性が高い**とわかった。今後の選択肢は
  実質的に次の2つに絞られそう。
  - 固定IPの回線・VPN経由での実行環境に切り替える
  - 「IPが変わって失敗する」前提を受け入れ、失敗時に即通知する仕組みだけ入れる
    （復旧作業自体はこれまで通り手動で許可IPを直す）

4回連続で同じ障害が起きているため、次回以降に着手するなら通知の実装を先にする方が
実利が大きそう（根本のIP問題は解消しないが、気づきが早くなる）。
