## 生成が止まっていた件

### 症状

`local/logs/` を見ると 8/29 11:28、8/30 11:04 に実行はされていて、どちらも
`403 CLIENT_IP_NOT_ALLOWED` で落ちていた。楽天のアプリ登録にある
「許可されたIPアドレス」に、いまの回線のIPが載っていないという意味。

### 原因

登録済みのIPは4件あった。

```
220.146.41.66
220.146.64.52
106.155.52.110
59.132.59.167   ← 追加したつもりのもの
```

実際の送信元は `59.132.56.172`。第3・第4オクテットが違う。

```
登録済み: 59.132.59.167
実 際 : 59.132.56.172
              ^^  ^^^
```

同じISPの近いレンジで見間違えやすいが、楽天は完全一致で判定するので弾かれる。
正しい値に直したところ、疎通確認は4エンドポイントすべて通った。

### 切り分けで潰した仮説

**IPv6で別アドレスから出ている可能性** — `openapi.rakuten.co.jp` は IPv4 でしか
解決されず、実際の送信元も ipify が返す値と一致していた。この線は消えた。
（この回線には IPv6 `2001:268:7390:...` もあるので、ありえた話ではある）

**資格情報の不備** — 生レスポンスが
`{"errors":{"errorCode":403,"errorMessage":"CLIENT_IP_NOT_ALLOWED"}}` で、
401でも400でもない。IP制限そのものだった。

**アプリの取り違え** — 楽天のアカウントにはアプリが2つある。

| アプリ名 | applicationId |
|---|---|
| ROOM投稿候補ジェネレーター | `a88aa8c5-...-6641bf4f6500` |
| モノ日々 | `f843e532-...-e6dafc09ebc4` |

`.env` の `RAKUTEN_APP_ID` は前者と一致しており、IPを追加した先も同じアプリだった。

### 途中で踏んだ誤り

切り分けの最初に `app.rakuten.co.jp/services/api/...` へ curl を投げて
`specify valid applicationId` が返り、資格情報が壊れているように見えた。
これは**旧エンドポイント宛ての無効なテスト**だった。本プロジェクトが使うのは
`openapi.rakuten.co.jp` の2026-07-01版で、`applicationId` に加えて `accessKey` が要る。
エンドポイントを合わせずに叩くと、原因を取り違える。
疎通確認は `python -m room.rakuten --smoke` を使えばこの間違いは起きない。

## 生成の条件（あらためて整理）

「PCが起動していなくても生成される」と思っていたが、**そうではない**。

`.github/workflows/daily.yml` の cron は無効化してある。楽天APIが登録済みIPからの
リクエストしか受け付けず、GitHub Actions のランナーは毎回別のAzure IPから走るため
全リクエストが403で落ちるから（ワークフローのコメントに実測runのURLがある）。

代わりにローカルPCのタスクスケジューラが担っている。

| 項目 | 値 |
|---|---|
| タスク名 | `RakutenRoom-DailyCandidates` |
| 実行 | `scripts/run_daily.ps1`（生成 → `docs`/`data` をコミット → push） |
| トリガー | 毎日 07:00 JST |
| `StartWhenAvailable` | True（7時に落ちていれば**起動後すぐ**に走る） |
| `WakeToRun` | True（スリープからは復帰。シャットダウン中は不可） |
| `LogonType` | Interactive（ログオンが要る） |
| 実行時間上限 | 30分 |

つまり「毎朝7時ちょうど」ではなく「**7時、またはその日の最初のPC起動直後**」。
8/29が11:28、8/30が11:03に走っていたのはこのため。

確認先は https://iroha0813.github.io/rakuten-room/ で、これは認識どおり。
ただし表示されるのは**最後に成功した生成結果**なので、
止まっていても「昨日のページが残っている」ようにしか見えない。

## テンプレートの固定化を解消した

### 実測した固定化

3日分15投稿を並べたら、想定より重症だった。

```
[0] 常に「困りごとを言い切る」  [1] 常に「使う場面」  [2] 常に「贈り物」
[3] 常に「仕様を1点」          [4] 常に「定番の理由」
ハッシュタグ 15/15 すべて3個   行数 7〜9行   字数 195〜246字
```

`room/write.py` が `angles[index % len(angles)]` で切り口を決めていた。
**順位だけで角度が決まる**ので、3番目が毎日「贈り物」枠になる。
8/28はスポンジ、8/30はノートPCが贈答品として紹介されていた。

さらに、1日5件に対して切り口は7個あるので、
`ANGLES[5]`（見落とされがちな利点）と `DEAL_ANGLE`（お得情報）は
**一度も使われたことがなかった**。

### 直した内容

**1. 切り口を日付シードで振り直す**

`plan_variations()` を追加。日付を種にして毎日組み替える。
同じ日に再実行すれば同じ結果が出るので再現性は保たれる。

**2. 「型」という軸を足した**

切り口（何を言うか）だけ変えても骨格が1種類だと同じ投稿に見える。
構成・分量・ハッシュタグ数をまとめて振る `FORMATS` を6種類用意した。

| 型 | 構成 | タグ | 目安 |
|---|---|---|---|
| フック→根拠 | 従来型 | 3 | 150字 |
| 問いかけ→答え | 問いで始めて答える | 2 | 130字 |
| 場面のスケッチ | 短い行を重ねて情景で見せる | 2 | 140字 |
| 箇条書き | フック＋「・」3項目 | 3 | 160字 |
| 短文で言い切る | 2〜3行、一点だけ | 1 | 80字 |
| 本音から入る | 留保・本音→着地 | 2 | 150字 |

型ごとに変わる指示はシステムプロンプトから商品ごとのプロンプトへ移し、
システム側には1行目の規則など**全型で共通のものだけ**を残した。

**3. 直近14日で使った切り口・型を後回しに**

`posted.jsonl` に `angle` / `format` を記録するようにした。
既存の履歴行にこの列はないが `.get()` で素通りする。
窓は `config/settings.yaml` の `llm.variation_window_days` で調整できる。

**4. ハッシュタグ数を検査するようにした**

そもそも検査が無く、だから15投稿すべて3個で揃っていた。
型が決めた個数を超えたら書き直させる。

### 結果

```
字数   195〜246  →   86〜198
行数     7〜9    →    5〜13
タグ    全部3個   →   1〜3個
```

テストは全192件パス。コミット `ad9d2b2`。

### 副作用

短い型・箇条書き型は絵文字が減りやすく、5件中3件で絵文字不足の書き直しが走った。
いずれも1回で通っている（API呼び出しは5→8回。Haikuなので影響は軽微）。

## 残していること

**失敗しても何も通知されない。** 今回3日ぶりに気づけたのは偶然で、
症状は「ページが昨日のまま」だけ。回線IPは今後も変わるので同じ形で必ず止まる。
対処するなら次の2つ。

- 失敗時に通知を出す（現状はログファイルに書くだけ）
- IPをCIDRで登録する。楽天の入力欄は `198.51.100.0/24` 形式を受け付ける
  （プレースホルダに明記されている）。`59.132.56.0/22` のように入れておけば
  同一ISP内の変動では止まらない。ただし許可範囲が広がることは理解した上での判断になる

**250字上限を超えた文がそのまま採用されることがある。** 8/30の生成では
ノートPCの紹介文が316字で、`llm.max_chars: 250` を超えたまま通った。
書き直しを1回試して改善しなかったときのフォールバックが初回の文を採るため。
ROOMの上限は500字なので投稿はできるが、設定は守れていない。
型ごとの目安字数が入って全体的に短くなったので頻度は下がるはずだが、
フォールバックの挙動そのものは手つかず。

**同種商品の重複。** 8/30はガジェット2件がどちらもWindows/Office付きPCだった。
`selection.max_per_shop: 1` はショップ単位なので、別ショップの似た商品は防げない。
