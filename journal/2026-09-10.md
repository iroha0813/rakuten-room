# 作業記録 2026-09-10（14日目）VPS移行後・初回cronの不具合対応

## 経緯

ユーザーから「本日の投稿って生成されてる？」と質問を受けて確認したところ、ローカル・
GitHub両方とも候補データが9/9止まりだった。[2026-09-09-2.md](2026-09-09-2.md)で
前日にOracle Cloud VPSへ移行し、cronを`0 7 * * *`（毎朝07:00 JST）で登録したばかりで、
今日がまさに初回自動実行日。現在時刻は11時前後で、予定時刻から4時間近く経っても
候補生成コミットが来ていなかった。

## 分かったこと

### 1. crondがopcのcrontabを一度も認識していなかった
`journalctl -u crond`を確認すると、rootの`cron.hourly`ジョブは記録されているのに、
opcの`run_daily.sh`に関する記録が設定時から一件も無かった（実行試行の形跡すら無い）。
SELinuxコンテキスト（`user_cron_spool_t`、正しい）、crontabファイルの中身、
`/etc/cron.allow`・`/etc/cron.deny`（どちらも存在せず、制限なし）は全て問題なし
だったため、原因は特定できていないが「crondが起動時か何らかのタイミングで
このユーザーのcrontabを読み込み損ねていた」状態だったと推測される。

`sudo systemctl restart crond`で再起動したところ、以降は`crontab -e`相当の操作で
crontabを触るたびに`crond[pid]: (opc) RELOAD (/var/spool/cron/opc)`のログが
正しく出るようになった。検証のため2分後に発火するテスト行を一時追加し、
実際に`run_daily.sh`が起動して9/10分の候補が生成されることを確認できた。
**再発時の切り分け方として「journalctl -u crondに対象ユーザーのCMD/RELOADが
一件もないか」を最初に見るのが有効**、というのが今回の学び。

### 2. git履歴の枝分かれが2つ重なっていた
昨日16:00のテスト実行（[2026-09-09-2.md](2026-09-09-2.md)に記載済み）でGitHubへの
pushが`[rejected] fetch first`で失敗しており、VM側のローカルリポジトリに
未push commit（`74bbcea`、9/9の余分な候補データ・履歴10件を含む）が残ったままに
なっていた。今日のcronテスト実行がその上に新しいcommit（`d36448b`、9/10の本物の
候補）を積んでしまい、二重に枝分かれした状態でpushが失敗し続けた。

解決手順：
1. `git reset --hard origin/main`でGitHub側の正しい状態（`dc9ffef`）に戻す
2. `git cherry-pick d36448b`で今日の生成分だけを載せ直す
3. `data/posted.jsonl`と`docs/index.html`でコンフリクト
   → `posted.jsonl`は「GitHub本物110行 + 今日の本物10行」を手で組み立て直し、
     昨日の余分な10件は破棄
   → `docs/index.html`は生成物なので今日の内容をそのまま採用
4. 未trackedだった`scripts/run_daily.sh`（[2026-09-09-2.md](2026-09-09-2.md)で
   新規作成されたが一度もcommitされていなかった）を別commitで追加
5. pushしたところ再度`fetch first`で拒否 → 原因はローカルPCで昨日行った
   README/journal更新（`6f6492b`）がGitHub側に先に反映されていたため。
   `git rebase origin/main`でファイルの重複がないことを確認しつつ解消し、push成功

## 残っている懸案

- **crondがcrontabを読み損ねた根本原因は未特定**。再起動で直ったが、次回VMを
  再起動した際に再発するかは分からない。しばらく`journalctl -u crond`で
  07:00の実行が続くか観察が必要。
- 09-11のセール終了後、[2026-09-03.md](2026-09-03.md)の設定変更を通常値に
  戻すのを忘れないこと（7日連続持ち越し）。
- 失敗時通知の未実装（[2026-09-09-2.md](2026-09-09-2.md)から持ち越し、
  `task_6cd37d5f`）は今回も未着手。今回のようにcronが「静かに」動かないケースこそ
  通知が無いと気づけないため、優先度を上げたい。
