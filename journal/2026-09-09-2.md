# 作業記録 2026-09-09（13日目・その2）IP恒久対策②を実施：Oracle Cloud無料枠VPSへ移行

## 経緯

[2026-09-09.md](2026-09-09.md)で本日分の候補生成対応後、ユーザーから「[2026-09-06.md]
(2026-09-06.md)で検討した②（無料枠VPS移行）は無料で構築可能なはずなので、それで進めたい」
と依頼を受けた。②を選んだ理由はユーザー確認済み：Oracle Cloud Free Tierは永年無料
（Always Free）でリソースが使え、固定パブリックIPも無料枠内。IP許可切れが9/4〜9/9で
8日連続発生していたことを踏まえ、恒久対策として着手した。

## 実施内容

### 1. Oracle Cloudアカウント・VM作成
ユーザーが新規にOracle Cloudアカウントを作成し、コンソール操作を引き継いだ。

- テナンシ: `irohatheabcsslp`、リージョン: Japan East (Tokyo)
- VCN (`rakuten-room-vcn`) をOracle公式の「Create VCN with internet connectivity」
  ウィザードで一括作成（パブリック/プライベートサブネット、IG、NAT、SG込み）。
  インスタンス作成画面内での「Create new virtual cloud network」は挙動が不安定
  （Public IPv4 assignmentのトグルが有効化されない不具合）だったため、独立した
  VCNウィザードに切り替えて確実性を優先した。
- インスタンス `rakuten-room-vps` を作成。Shape: `VM.Standard.E2.1.Micro`
  （AMD, 1 OCPU / 1GB memory, Always Free-eligible）、Image: Oracle Linux 9.8。
  ARM版（A1.Flex、最大4 OCPU/24GB）も無料枠内で選べたが、今回の用途（軽量な
  定期実行）には十分と判断しE2.1.Microのまま進めた（後述のとおりメモリ不足で
  苦労したため、次回同様の作業をするならA1.Flexを検討する価値あり）。
- SSH鍵: 最初にEd25519鍵を生成したが、Oracle Cloud側のインスタンス作成フォームで
  "There should be spaces between parts of the key" という紛らわしいエラーで
  拒否された。原因はEd25519鍵タイプそのものが弾かれていたことで、RSA 2048bit鍵に
  切り替えて解決。

### 2. 固定IP化
作成直後のPublic IPはephemeral（一時的）だったため、VNICの「Reserve IPv4 address」
操作でephemeral→reservedに変換（IPアドレス自体は`158.101.141.44`のまま変わらず）。
操作時に一度別のReserved IPを誤って新規作成してしまったが未使用のまま削除し、
実際にVMにアタッチされている158.101.141.44の方を確定させた。

### 3. VMがメモリ不足で2回ハング → 復旧とスワップ増強
`VM.Standard.E2.1.Micro`は1GBメモリのみで、`sudo dnf install -y git` 実行中に
2回SSH接続が完全に応答不能になった（Connection timed out）。Monitoringタブで
CPU/メモリ使用率が急上昇しているのを確認し、OOM相当の状態と判断。

- 1回目・2回目とも Actions → Reboot instance →「Force reboot」（即座に電源
  off/on）で復旧。通常のReboot（ACPIシャットダウン待ち）ではなく強制リブートが
  必要だった。
- 復旧後、`/swapfile2`（2GB）を追加作成し、スワップ合計を944MB→2.9GBに増強。
  これ以降は同じdnf処理でもハングせず完走するようになった（gitインストールは
  スワップ増強後に成功）。
- 対応中、ユーザーから「このまま待てば完了するか、断念judgeが必要か」と問われ、
  判断基準を明示：バックグラウンドタスクの実際の完了確認（git --versionで
  検証）とVMの応答性（free -h, ps aux）を根拠に「待てば完了する」と判断した。
  以降の重い処理は「5分待って応答なければ断念してARM版に作り直す」を基準にした
  （実際には発動しなかった）。

### 4. Python環境・リポジトリ配置
- room/以下のコードは`from __future__ import annotations`を全ファイルで使用して
  おり、PEP604の型ヒント（`str | int`等）があってもPython 3.9で問題なく動作する
  ことをローカルでgrep確認。Oracle Linux 9標準のPython 3.9をそのまま使うことに
  決め、3.12を探すための追加dnf作業（再度ハングのリスク）を回避した。
- `git clone`でリポジトリ配置 → `python3.9 -m venv .venv` → pip install →
  `pytest -q` で全106件通過を確認。

### 5. 秘密情報とGitHub連携
- ローカルの`.env`をscpでVMへ転送（内容はクライアント側に一切表示せず転送、
  権限は600に制限）。
- VM上で新規SSH鍵ペア（`github_deploy_key`）を生成し、公開鍵をGitHubの
  Deploy Keys（Read/write）として登録。登録の最終確認（GitHubのsudo mode /
  メール認証）はユーザー本人に実施してもらった（エージェントが代行できない
  操作のため）。
- `git remote set-url origin git@github.com:iroha0813/rakuten-room.git`に変更し、
  `GIT_SSH_COMMAND`でdeploy keyを明示指定してfetch/pushが通ることを確認。

### 6. cron設定
- VMのタイムゾーンはデフォルトGMTだったため`Asia/Tokyo`に変更（UTCのまま
  07:00に実行すると候補生成の日付がJSTの日付と1日ずれるため）。
- `scripts/run_daily.sh`を新規作成（`run_daily.ps1`のbash移植）。ログ出力、
  git add/commit/push、エラー時のメッセージは元のPowerShell版を踏襲。
- `crontab`に`0 7 * * *`で登録。`crond`がactive/enabled であることを確認。
  cron実行時の最小PATH環境でも`git`/`python3.9`が解決できることを
  `env -i PATH=... which git python3.9`で検証済み。

### 7. 動作確認とトラブル
楽天API側のIP許可反映を待ってから`room.collect --dry-run`で疎通確認 → 成功
（300件収集）。続けて`run_daily.sh`を本番実行して一連の流れを検証したところ、
**これが本日2回目の本番候補生成になってしまい**、朝ユーザーが投稿作業に使った
候補（サバ切身・菊芋桑茶等）が新しい候補（ベーグル・近江牛等）で上書きされる
事故になった。ユーザーに即座に報告して確認したところ、「今朝の投稿は完了済み
なので上書きされても実害なし」との返答で事なきを得たが、`data/posted.jsonl`
には本日分の提示済み履歴が10件→20件（本来投稿していない10件を含む）に
なっている。実害は「その10商品が今後の候補から永久に除外される」程度で軽微
だが、**動作確認のつもりの実行が実際に本番副作用（GitHubへのpush・履歴更新）を
伴うことを見落としていた**のは反省点。次に同様の確認をするときは`--local`
オプション（LLMを呼ばず履歴も更新しないモード）を使うべきだった。

### 8. Windows側の後片付け
